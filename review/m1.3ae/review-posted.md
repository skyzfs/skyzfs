### What you asked me to judge

**1. The simulated disk's per-file block size.** Consistent where it is used, with two gaps.
- **Where it is used.** `block_size_of` replaces the disk's block in exactly the three places that read it for a file:
  - the reach of a write through the cache;
  - the reach of a deallocation;
  - `File::block_size`.
  
  `Dir::block_size` keeps the disk's. A direct write still writes only its own sectors. Nothing in a power cut touches `block_sizes_of`, so it holds across one, and the sim test checks that.
- **Not tested: a deallocation's reach.** Plant S2 makes `deallocate` use the disk's block for a file of its own, and nothing fails. The sim test writes but never deallocates. A `deallocate` of one sector inside the file's own block, then a garbage cut, would hold it, in the same shape as the write's lines.
- **"Goes with the name" makes a rename onto that name a move to the other file system.** `block_size_of` looks the name up at every use.
  - So a file renamed onto a name that was given a block size takes it on.
  - On Linux that cannot happen: a rename onto a mount point is refused (`EBUSY`), and a rename onto a symbolic link replaces the link, which leaves the file on the directory's file system.
  - The store does rename onto `HOME_NAME`: `create` writes `HOME_NEW_NAME` and renames it (start.rs:353). A test that set the home image's block size before a create would see the new image "on its own file system", which no real create can make.
  - No test does that today. Say it in the doc of `set_block_size_of` (set it after the file exists, and a rename onto the name is not modelled), or key it by the file and not the name.
- A smaller edge, for the doc too: a file that has lost its name (removed while open) falls back to the disk's block.

**2. A refusal that does not fail the volume.** The right reading.
- The directory's refusal (`Blocks { what: Directory }`) already fails nothing, and the home image's is the same kind of thing. The image is where the operator put it, nothing was written, and nothing shows that data was lost.
- Failing the volume would ask for an acknowledgement of a loss that did not happen.
- The test holds every part of it:
  - no marker;
  - the names and the counts of writes and syncs unchanged;
  - a start that serves once the image is back on the disk's file system.
- The daemon sorts it as a refusal with its own words (`volume/tests.rs`).

**3. What else reaches the home image's file system.** Nothing at the open that is still untested.
- **The direct-I/O check** (`STATX_DIOALIGN`, `fs.rs:610`) is a `statx` on the image's own direct descriptor, so it is per-file by construction. There is no directory-level check that it could be confused with. The sim's direct-I/O setting is disk-wide, which is enough for that reason.
- **Deallocation support, the cache drop and the syncs** act on the image's descriptor at run time.
- The real directory opens the image with `std::fs::OpenOptions`, which follows a symbolic link, so "a link elsewhere" is a real case, as the test's doc says.

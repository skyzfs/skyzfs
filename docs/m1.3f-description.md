## Work package

M1.3f: a write-zeroes record deallocates its range in the home image. Before, a checkpoint wrote the record's whole length in zeros, for a record that is one header in the log: a step of the daemon's took eight records of 1 MiB, 32 KiB of log, and behind a log of them a request of 1 MiB waited for 33 steps and 264 MiB of zeros (measured in skyzfs/skyzfs#19: the first 128 MiB written to a pool behind such a log took 131 s and 81 s). Now nothing is written for such a record, and a request waits for one step.

Commits: `73eff63..f7796cc` on `zfs-topology`: three commits of its own (8110663, d82f708, 058174f), four from the review round (616e1fd, 7d7c35e, a4b51bf, 5d6814e), and two merges of `zfs-topology`: 5486d01 at 8899c01 (M1.T7, skyzfs/skyzfs#20: the rigs on the daemon) and f7796cc at 32283c6 (M1.T7a, skyzfs/skyzfs#22: a row of the control rig's table), which changed no product code. The control rig's exit 2 on this pull request's earlier heads was that missing row (`control_test_program_self_delete: not in the table EXPECTED`), not a verdict on the binding. Design: docs/skyzfs-design.md §5.1 ("A step that takes less than a request adds does not break the bound", and the paragraph after it).

What 058174f does:

- **A call of the `File` trait, `deallocate(offset, len)`**: the range reads as zeros, has no space behind it, and the file keeps its length. Linux: `fallocate` with `FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE`, through `rustix` (already a dependency of the daemon; no `unsafe`). `EOPNOTSUPP` and `ENOSYS` are answered as "unsupported", having changed nothing. macOS `fcntl(F_PUNCHHOLE)` and Windows `FSCTL_SET_ZERO_DATA` on a sparse file are named in the trait's text and not built; those platforms answer "unsupported" until they are.
- **The store applies a write-zeroes record by deallocating its range** and writes nothing for it. The record counts no bytes in a step's bound, as a discard counts none, so a step takes up to its count of records (1024 in the daemon: 4 MiB of log, more than a request adds).
- **A file system that cannot deallocate is not a failure**: zeros are written, as before, for that record and from then on; each such record counts its length again, so a step still writes at most its bound, and the cost of #19's table is back for that volume. The store says which path a volume is on (`LogState::zeroes`: untried, deallocated, written), and so does `skyzfsd status`, in a new line `zeroes_applied`. The status file is version 4 (`SKYZSTA4`, 200 bytes, one field at offset 192); version 3 is still read, without that line.
- **An I/O error from the call fails the volume**, like any failed write into the home image. The log keeps the record and the next open applies it again.
- **Which path a volume is on is found out by the first write-zeroes record a checkpoint applies after an open.** Until then such a record counts its whole length, so a step keeps to its bound whichever it turns out to be. I chose this over a probe at the open: a probe would need a file of its own in the volume's directory, or a hole punched somewhere in the home image before any record asks for one.
- The simulated disk models the call (below), can refuse it and can fail it. The test build of the daemon has `serve --refuse-holes`, which makes the store behave as on a file system without holes.

### The points the package was asked to settle

- **Edges.** The store deallocates the record's whole range, which is of whole 4 KiB blocks, and does not cut it to write units. Where the write unit is larger (16 KiB on Apple silicon) and the range covers its first or last unit only in part, the file system zeroes that part of the unit by a write, which rewrites the unit as any write does. So the other blocks of those two units are saved as preimages before the range is deallocated: the rule and the code are the ones for a write there, unchanged (`protect_neighbours` already took the first and last unit of a write-zeroes record's run). "No preimage" holds exactly where volume block, file-system block and write unit agree, or the range covers whole units: the set of neighbours is then empty by the same computation. The units inside the range take no neighbour with them.
- **Durability and tearing.** A hole is durable when the home image's sync has returned, like a write; the step's order is unchanged, so the log gives up the record only after that sync. The simulated disk models a hole that is not synced as one more version, zeros, of each of its sectors, so a power cut leaves each block as it was or as zeros; the sectors of the two edge units outside the range get a pending version too, as by a write, so a cut that makes garbage of what was being rewritten makes garbage of them. (The same cut also makes garbage of the hole's own sectors, which is more than a hole can do; the store survives it because the log has the record.) `steps_of_holes_and_writes_can_be_cut_anywhere` cuts the power after every number of writes, deallocations and syncs from 0 to 29 and at six later points, over 128 groups of a range that begins and ends inside a write unit and a write beside it, in all eight environments; the open that follows is cut as well.
- **What a read of a hole returns.** While the record is in the log a read of its blocks is answered from the index, with zeros, without the home image. After the step the index lets go and the home image is read, where a hole reads as zeros (asserted on the simulated disk and on a real file). The store keeps no other copy of a block: there is no block cache yet, and the pump's copies of first writes are buffers of requests in flight, not of blocks. When the cache of design §5.1 is built it must treat a hole as a write of zeros; that is a note for that package.
- **Refusal against failure.** "Unsupported" falls back and says so; anything else fails the volume. Both are tested, with the mutants "the refusal fails the volume" and "written zeros count nothing in the bound".
- **Which errors fall back and which fail the volume.** Two fall back: `EOPNOTSUPP` (the file system has no such operation, or not this mode of it) and `ENOSYS` (the kernel has no `fallocate`). Both are answered before anything is changed. Every other error fails the volume, with the record still in the log. What a real file system can answer besides, from `fallocate(2)` and from what I know of ext4 and XFS; none of it is tested here:
  - *A range that is not of whole file-system blocks.* ext4 and XFS do not refuse it: they deallocate the whole blocks inside the range and zero the partial blocks at its ends by writing them. The preimages cover that as far as the store's write unit reaches, which is the page size (`Identity::system_write_unit`): a file system with 64 KiB blocks on a kernel with 64 KiB pages is covered, because the two partial blocks are units whose other blocks were saved. A file system whose block is larger than the write unit is not, and there a range is not deallocated (review round, below). `EINVAL` for an unaligned range is what `fallocate` documents for collapsing and inserting a range, not for punching a hole; hugetlbfs is the one I know that wants aligned holes, and a volume does not live there.
  - *`EPERM`*: the file is immutable or append-only, or sealed. A home image in that state cannot be written either, so the volume would fail at its first write in a step whatever the store did about the hole.
  - *`ENOSPC` or `EDQUOT`*: possible, since splitting an extent can need a block of metadata; *`EIO`*; *`ETXTBSY`* for a swap file. All fail the volume, as the same errors from a write do.
  - So on the daemon's ordinary volumes (ext4 or XFS with 4 KiB blocks; ZFS is refused) only the first two and the real failures can occur, and I know of no file system among those a volume would be put on that answers `EINVAL` to this call. If one does, the volume fails where it could have fallen back: an `EINVAL` changes nothing, so treating it like "unsupported" would be safe. I have not done that, because a wrong argument of our own would then be hidden as a slow path; say if you want it.
- **Platforms.** Linux only, as above.
- **A discard is unchanged**: recorded for the cut, nothing changes locally, and a read after it returns what was there, which the store's tests assert. I found no reason to change it here: freeing the space would change what a discard does to reads, and is not part of making write-zeroes cheap.
- **The reviewer's suggestion on #19** (the gate at the high mark only for a request that appends): not worth its code now. Behind writes, discards and deallocated write-zeroes a request waits for one step, so a read at the front would save at most that one step. The cases where it would save more are a volume on a file system without holes and record alignment 64, neither of which is the daemon's ordinary case.

### Review round: a file system whose block is larger than the write unit

Finding (the lead, on this pull request): the rule that saves a range's neighbours reaches as far as the write unit, which is the page size. A file system can have blocks larger than a page (XFS since Linux 6.12). A hole aligned to 4 KiB that ends inside such a block has the file system zero the part by writing the block, so blocks of the volume beside the range are rewritten with no preimage.

Answer, commit 616e1fd: where the path is chosen (the first write-zeroes record a checkpoint applies after an open), the store asks the file system's block size through a new call of the `File` trait, `block_size` (Linux: `f_bsize` of `fstatfs` on the home image), and deallocates only when it is no larger than the volume's write unit. Otherwise, and when the size cannot be read, zeros are written, as on a file system that cannot deallocate, and the store says which reason: `LogState::zeroes` has a fourth state, the status file's field takes the value 3 (same version 4, same length; a reader that does not know 3 reads "not said"), and `zeroes_applied` reads "written as zeros: the blocks of the volume's file system are larger than the store's write unit, or their size could not be read, ...". The simulated disk has a block size (`SimDisk::set_block_size`, one sector unless set), and a hole that ends inside a block rewrites the block's other sectors as it did a write unit's.

Tests: `a_range_is_deallocated_only_where_blocks_are_no_larger_than_the_write_unit` (blocks of four and of two units, and a disk that does not say: the fallback, nothing deallocated, the store says why; blocks of one unit and of 512 bytes: deallocated) and `a_write_zeroes_inside_a_larger_block_can_be_cut_anywhere` (a block of four units, one unit zeroed in its middle, the checkpoint stopped at each of its first twelve operations and the power cut with garbage: the rest of the block holds what it held). Both fail in all eight environments with the mutant "the block size is not asked". On the simulated disk, `a_hole_that_ends_inside_a_block_rewrites_the_block`; on a real file, `a_real_file_says_its_file_systems_block_size`.

What I did not verify, and what it costs:

- I have no source at hand in this container for what XFS does at a partial block larger than a page, or for `f_bsize` on each file system. From what I know: ext4, XFS and btrfs report their block (sector) size there, and tmpfs the page size; a network file system reports its transfer size, which is usually larger than a page, so a volume on one takes the fallback though a hole there may be harmless. That errs to the slow side and says so in `status`.
- **The same exposure exists for an ordinary write, and is older than this package.** The write unit is the store's one assumption about how far a write reaches: the log never writes again into a unit that holds a durable record, a checkpoint saves the other blocks of each unit it writes in part, and nothing more. The log's segment files, the preimage file and the home image are all written through the page cache (direct I/O is used only for the device read), and on a file system with blocks larger than the write unit the kernel writes back whole blocks. This package closes the hole's half. The whole is closed at the unit by the next package, M1.3g (a volume's write unit is at least the block size of the file system its directory is on, chosen or refused at create and checked at every open), which reuses `File::block_size`. Until it merges: **a volume's directory must be on a file system whose block is no larger than the page**, which holds for ext4 and for XFS as `mkfs` makes them by default.

### Review round: the reviewer's three findings, and a kernel test of the binding

1. *No test had a write inside a range an earlier record zeroed.* Added, a4b51bf: `a_write_inside_a_zeroed_range_can_be_cut_anywhere`, as the reviewer wrote it: a write-zeroes over blocks 1 to 5 and a write of block 3; in every third group a second write-zeroes over blocks 2 and 3 and a write of block 2; steps of at most five records, so a step often ends between a write-zeroes and the write into its range; the steps stopped at 46 points and the power cut, the open cut again; checked after the open, after the remaining steps and after one more open. It catches the same two mutants as the test beside it (the log is reclaimed before the home image is synced; no preimages). I did not search the other mutants for one that only this test catches.
2. *The state can go from deallocated to written inside one step*, which was sized with write-zeroes counting nothing: up to 1024 records of 1 MiB written in one step. Fixed, a4b51bf: the batch ends with the record at which the refusal came (that record's zeros are written, the log is given up to its end), the step reports what it took, and the next steps are sized by what they write. A whole checkpoint applies the rest of its batch as one more. Test by the hook: `a_step_ends_where_the_file_system_first_refuses_to_deallocate` (the step with the refusal takes one record of 16 blocks; the 22 records after it take 11 steps of two; nothing lost, the volume not failed; and the same refusal inside a whole checkpoint). Mutant: the step goes on.
3. *`EINTR`.* Fixed, 7d7c35e: a deallocation that a signal interrupts is made again, and so is the `fstatfs` behind `block_size`; the retry has a unit test. Which threads take the daemon's signals: none but the main one, and it only by asking. `signals::block()` blocks SIGTERM, SIGINT and SIGUSR1 in `serve` before `run` starts any thread, so every thread, the store's worker included, inherits the mask, and the signals are taken only by `sigtimedwait` in the main loop. A stop signal therefore cannot interrupt a deallocation, a write or a sync of the worker. For any other signal: the store's reads and writes go through the standard library's `read_exact_at` and `write_all_at`, which make an interrupted call again, and its `sync_data` does the same inside; the calls through `rustix` were the only ones that did not.

*The binding's kernel test of the buffers failed once* (`data_of_4k_and_1m_is_whole_in_one_life_and_across_a_take_over`, run 43130686991 on Ubuntu 24.04: "0 first-write copies after the take-over", with both exact checks passed). Not from this package's change: every tag's first request after the take-over was a read of somebody else's, most likely udev's, which reads a device after a writer closes it and whose reads wait through the take-over. Fixed in the test, 5d6814e, by both of two things: it waits for udev (`udevadm settle`) before a life ends, and it repeats the life after a take-over, up to three times, until one has a first write, failing only if none has and saying how many were tried. The exact accounting of every life is kept. It still assumes that no other reader takes every tag first three lives in a row. The repeated lives run only when the first had no first write, so an ordinary run does not exercise them; the control rig on this pull request is the test's first run on a kernel.

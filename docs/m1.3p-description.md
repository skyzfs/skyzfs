## Work package

M1.3p: the readers' queue wakes one thread per read.

M1.3n gave a served store several reader threads (`serve --readers N`, 4 unless given). In the benchmark after it, the readers' CPU together rose from 4.5 to 7.8 s unbounded for the same reads, and from 7.5 to 11.0 s at 1 GiB. The cause was the queue the readers shared: a channel's receiver behind a mutex.
- The idle reader that held the mutex was parked in `recv()`; the others were parked on the mutex.
- A read woke the holder. When it let go of the mutex, the unlock woke a second reader, which took the mutex and went into `recv()` on an empty channel. That `recv()` spins and yields before it parks.
- So every read cost two wakes and two context switches.

This package replaces that queue and changes nothing else (design §5.1 "Reads leave the worker").

Commits: `35e5c40..00f4440` (one commit, 00f4440) on `skyzfs-coding`, restarted at `zfs-topology` 35e5c40. Files: `crates/skyzfs-local/src/store.rs` (the queue `ReadQueue`, its use in `Store::serve_with` and `Served`, two mutants) and `crates/skyzfs-local/src/store/tests.rs`.

## Not done, and open questions

- **Four readers still cost more CPU per read than one** (22.4 against 17.2 µs here, one run each). The second wake is gone (switches per read 1.00). I have not measured where the rest goes. Candidates, not checked: the reader woken need not be the one that read last (the order of a futex's waiters is the kernel's), so the thread that reads finds its caches cold; and the shown times are one mutex for all readers.
- **The 100 ms window** in `a_read_wakes_one_waiting_reader` is the one bound on time in these tests (explained above). It costs 100 ms per run of the test.
- **No kernel run of mine**, and no benchmark: the rigs and the testing session's round are what show the effect on the daemon.

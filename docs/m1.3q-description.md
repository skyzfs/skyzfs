## Work package

M1.3q: the ublk feature flags the daemon needs, and the kernels that have them.

Before this package the daemon checked one thing at its start, that the driver could reissue (`UBLK_F_USER_RECOVERY_REISSUE`), and named no kernel. Now one module, `skyzfs_ublk::features`, names everything the daemon needs from the ublk driver, with the kernel release that brought each and where that fact was read. A start, and a detach, check all of it before they touch anything, and a refusal names what is missing and the oldest kernel that has it.

## The flags, the commands and their kernels

| What | Bit | Why the daemon needs it | First release | Read at |
|---|---|---|---|---|
| `UBLK_F_USER_RECOVERY` | `1 << 3` | a device waits for a server when its server ends | 6.1 | header v6.0 (absent), v6.1 (present); `ublk.rst` v7.0 |
| `UBLK_F_USER_RECOVERY_REISSUE` | `1 << 4` | requests in flight at a server's end go to the next server | 6.1 | header v6.0 (absent), v6.1 (present); `ublk.rst` v7.0 |
| `UBLK_F_CMD_IOCTL_ENCODE` | `1 << 6` | the daemon's own control commands are ioctl-encoded (`UBLK_U_CMD_*`), with no fallback | 6.4 | header v6.3 (absent), v6.4 (present) |
| `UBLK_U_CMD_GET_FEATURES` | a command | the start reads the features word with it | 6.5 | header v6.4 (absent), v6.5 (present); driver v6.4, v6.5 |
| `UBLK_U_CMD_DEL_DEV_ASYNC` | a command, no feature bit | the delete of a device a client still holds, which is how a failed volume gives up its device | **6.11** (named from 6.9) | header v6.8 (absent), v6.9 (present; the v6.8 to v6.9 diff of the header adds only it). Driver v6.9 and v6.10: not executed (see below). Driver v6.11: executed |
| **Oldest kernel** | | the newest of the above | **6.11** | |

**The asynchronous delete: named in 6.9, executed from 6.11.** The review found this, and I checked it in the driver. In `drivers/block/ublk_drv.c` at v6.9 and at v6.10, the control commands are matched by `switch (_IOC_NR(cmd_op))` (line 2890 in both). But this command's case is labelled with the whole `UBLK_U_CMD_DEL_DEV_ASYNC` (line 2907), which `_IOC_NR` of a command never equals. So the command falls to `default: ret = -ENOTSUPP` (line 2926), errno 524. v6.11 defines `UBLK_CMD_DEL_DEV_ASYNC` as `_IOC_NR(UBLK_U_CMD_DEL_DEV_ASYNC)` (line 52) and matches that (line 2911). A 6.9.y or 6.10.y stable release that carries the fix is the override's case, like a backport. The other entries were checked in the driver as well, at the releases given: the three flags are in the driver's `UBLK_F_ALL` at v6.1 and v6.4, and v6.5 matches `_IOC_NR(UBLK_U_CMD_GET_FEATURES)`.

**Sources.** git.kernel.org could not be reached from the container that did this (the proxy refused it), so every fact was read from the mirror of the kernel's tree at github.com/torvalds/linux, through raw.githubusercontent.com, on 2026-11-12:
- `include/uapi/linux/ublk_cmd.h` at every release tag from v6.0 to v7.0. For a flag or for `UBLK_U_CMD_GET_FEATURES`, the release given is the first tag whose header defines the name and whose driver acts on it; for those, the two releases are the same. For the asynchronous delete they differ, and the release given is the driver's.
- `drivers/block/ublk_drv.c` at v6.1, v6.2, v6.3, v6.4, v6.5, v6.8, v6.9, v6.10, v6.11 and v7.0, for what the driver answers and executes.
- `Documentation/block/ublk.rst` at v7.0, for what the recovery flags mean.

The commits that added each name were not looked up: the release tags bound them. No entry is unverified.

**What the driver answers**, read in the driver's source:
- From v6.5 it answers `UBLK_U_CMD_GET_FEATURES` before it looks for a device, with `UBLK_F_ALL`, which holds all three flags.
- Before v6.5 the command, sent for device number `u32::MAX` (never a device's), answers `ENODEV`. In v6.3 and v6.4 that is because the driver looks the device up before it matches the command. In v6.1 and v6.2 the answer is set to `ENODEV` before a switch on the whole command, and that switch knows no ioctl-encoded command. The daemon reads that answer as "no such command".
- An unknown command answers `ENODEV` for a device that does not exist, and `ENOTSUPP` once the device is found. So nothing tells a driver that executes `UBLK_U_CMD_DEL_DEV_ASYNC` from one that does not, short of adding a device and deleting it.

The library under the queue (libublk 0.4.8) asks for no flag of its own for a device the daemon added. It uses the ioctl encoding for the queue's commands when the device reports `UBLK_F_CMD_IOCTL_ENCODE`, and the legacy encoding when not.

## After review

The review session's findings, at 0ddab81, and what f1b4d52 does with each:
1. **The asynchronous delete's floor is 6.11, not 6.9** (blocking). The header names the command from 6.9, but the drivers of 6.9 and 6.10 do not execute it; see the table above, with the lines. `DELETE_KERNEL` and `OLDEST_KERNEL` are 6.11, and the messages, the help and the tests say so: "6.9", "6.9.0", "6.10-rc1" and "6.10.3" refuse, and "6.11" and "6.11.0-29-generic" serve. Without the change, the tests fail: those four releases are in the refused set.
2. **A delete the driver does not know.** `raw::delete` turns `ENOTSUPP` (524) into an error that says what it is (`features::delete_not_executed`, tested): "the ublk driver of this kernel does not execute UBLK_U_CMD_DEL_DEV_ASYNC (it answered ENOTSUPP, 524), so device N could not be deleted and was not given up. The driver executes it from Linux 6.11; if --kernel-has-async-delete was given, this kernel does not have it".
3. **A refused start and a waiting device.** There is no change in behaviour: the check still comes before the record is read. The refusal now says that a device of the volume that waits for a server, if there is one, still waits. When the release is what refused, it also says what the option does (see the second round below). This is `serve::not_served`, and it is tested.
4. **Wording.** The module now says that the drivers of v6.1 and v6.2 preset `ENODEV` before a switch on the whole command, and that v6.3 and v6.4 look the device up first. The help says what `serve` and `detach` do before their check, instead of "before serve or detach touches anything".
5. **A missing control device.** `ENOENT`, `ENODEV` or `ENXIO` from opening `/dev/ublk-control` is now "the ublk control device /dev/ublk-control is not there (is the driver loaded?)", for every command (`raw::control_missing`, tested). Before this, the features command read it as a driver without the command.

The review's second look, at f1b4d52, found that the pull request can merge, and left three points that do not block. 0f5b7dc answers them:
1. The refusal says that `--kernel-has-async-delete` lets a start go on only when the release is all that lacks (`Unsupported::only_by_release`). When a feature lacks too, it says that the option alone does not let a start go on. Linux 6.1 to 6.4 are such kernels: they lack the features command as well as the release. A test covers both cases, and with `by_release` planted back in the place of `only_by_release`, it fails.
2. The refusal no longer says "Nothing was touched", since the run directory has been made by then. It says: "No device was added, taken over or deleted, and the volume's lock and store were not opened".
3. The reading of `ENOTSUPP` from the delete is `features::delete_answered`, a function of the driver's answer, and it is tested without a kernel. 524 gives the named error with no errno left, and any other errno passes through unchanged. Before this commit, the mapping sat inside the call to the kernel, and no test failed when it was planted out.

## Not done, and open questions

- **The asynchronous delete is judged by the release, not detected.** A kernel of 6.11 or later whose driver does not execute the command (a distribution that took it out) would pass the check and fail at its first delete. A kernel below 6.11 with the command backported, or a 6.9.y or 6.10.y with the fix, is refused unless the operator says so. There is no way to tell from the driver without adding and deleting a device. The review proposed such a probe, and the lead did not take it: it would add and remove a device at every start, and a daemon killed between the two would leave a device nobody owns.
- **The override is the operator's word and is not checked.** On a kernel without the command, a start with it serves until a failed volume must give up its device, and that delete fails. The delete's error then says that this driver does not execute `UBLK_U_CMD_DEL_DEV_ASYNC`, that the device was not given up, and names the option, instead of "Unknown error 524". The help says to give it only for a kernel whose driver is known to have the command.
- **My readings, marked in the code:**
  - A detach with no record of this boot does not check the kernel (above).
  - The detach checks after it has taken the volume's lock. The check changes nothing, so it does not matter whether it comes before or after the lock. After the lock it costs nothing when the volume has no record.
  - The release is read from `/proc/sys/kernel/osrelease`, without its line's end, and not through `uname(2)`. Both give the same string.
- **`ENODEV` for the features command is read as "no such command"** only because the command is sent for a device number that is never a device's. A driver of 6.5 or later answers before any lookup. An `ENOENT`, `ENODEV` or `ENXIO` from opening the control device is told as "the ublk control device /dev/ublk-control is not there (is the driver loaded?)", with no errno left on the error, so it cannot be taken for that answer.
- **Not in scope, as the package says:** supporting an older kernel by changing what the daemon asks for, the zero-copy flags, the NBD fallback.

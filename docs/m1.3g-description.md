## Work package

M1.3g: a volume's write unit is at least the block size of the file system it is on.

The write unit is the store's one assumption about how far a write reaches beside what it writes. The log never writes again into a unit that holds a durable record, and a checkpoint saves the other blocks of each unit it writes in part; nothing else is protected. The write unit was the page size. All three of a volume's files (the log's segments, the preimage file, the home image) are written through the page cache, and a file system writes back whole blocks: on one whose block is larger than the write unit (XFS with blocks above the page size, since Linux 6.12), a write rewrites sectors beyond its unit, and a power cut can lose them with nothing to restore them from. skyzfs/skyzfs#21 closed this for a deallocated range only. This package closes it at the unit.

Commits: `44fb9e9..6a501fb` on `zfs-topology`: 06b77f9, and c13f59e and 6a501fb from the review round. Design: docs/skyzfs-design.md §5.1 (the limit written there at #21's merge).

## What was done

| asked | done |
|---|---|
| 1. `create` chooses the write unit | `skyzfsd create` takes the larger of the page size and the block size of the directory's file system (`Identity::write_unit_for`), and refuses, with the reason and "Nothing was done", a block above 65536 bytes, one that is no power of two, and one that cannot be read. The store's own `create` refuses a directory whose block is larger than the unit it was given, before it makes anything, the lock file included |
| 2. Every open that will write checks again | `Store::open` and `open_locked` (there is no other open): before anything is read, recovered or written, the store reads its write unit from the superblock and compares. Larger, or unreadable: `StoreError::Blocks` / `BlocksUnknown`, nothing changed |
| 3. All three files | A check per file, and the directory: at an open, the block size of the directory and of every file the store writes in it (the home image, the preimages, `log.*`) |
| 4. The simulated disk and the tests | An ordinary write now rewrites the whole file-system block around it, in every file. Tests below |
| 5. #21's rule and the fourth state | Removed from the store; the status file's value 3 stays readable. Reasons below |
| 6. No format change | None. The identity in the superblock already carries the write unit (`Identity::write_unit`, 4096 to 65536, a power of two); a volume made on larger blocks only has a larger value in that field |

| 8. What §5.1 should say; what is not verified | Last two sections |

### The decisions asked for

- **Which call at `create`, and why.** The directory's (`Dir::block_size`, new: `statfs` of the path on Linux). At a creation there are no files yet, and every file of a store is created in that directory under a name that did not exist, so it is on the directory's file system. That also covers files made later (new log segments, the preimage file).
- **At an open: the directory and every file the store writes.** A name can lead to another file system than the directory's (a symbolic link put there by hand, a file mounted over a name), so the open asks each of the store's files that is there (`File::block_size`, from #21) as well as the directory. This is why the answer to "one directory, one file system, or a check per file" is both.
- **A size that cannot be read: refused**, at `create` and at an open, as you proposed. I see no argument against: the assumption cannot be checked, and guessing "one page" is exactly the case this package is about. The cost: macOS and Windows have no such call built (`Unsupported`), so no store can be created or opened there until they do. Nothing runs there today.
- **A network file system that reports its transfer size** as its block size: with 64 KiB or less (and a power of two) the volume is made with that as its write unit; with more, typically 1 MiB, `create` refuses and says the size. That refuses volumes that might be safe. I do not know what such a file system really rewrites around a write, and the daemon's volumes are node-local, so I left it refused.
- **What a larger write unit costs.** The log starts the first record after every sync at the next unit, so a volume with a 64 KiB unit pads up to 64 KiB per flush, and a checkpoint saves up to the rest of a unit beside each partial write. That is the format working as designed for 64 KiB pages; it is not measured here.
- **The refusal at a start.** `skyzfsd serve` reports it through the existing path for an open that fails without a failed volume (`OpenError::Other`): the line `opening the store: <what> is on a file system with blocks of N bytes, larger than the volume's write unit of M bytes: a write there reaches beyond what the store protects`, exit status 1 (`Exit::Error`). No failure note is written, the log is not marked, and no device is deleted; `status` afterwards shows what it showed before. The daemon takes the volume's lock before the open, so the lock file may be made in the directory; nothing of the store is written.
- **Read-only tools.** There are none that open the store: `status` and `detach` read the records and the status file and take at most the lock. Every open of a store is a recovery that writes, and every one goes through the check.

### 5. #21's rule is removed

#21 deallocated a range only where the home image's file system had blocks no larger than the write unit, wrote zeros otherwise, and said so in a fourth state (`zeroes_applied`, status value 3). After this package:

- It cannot be reached: an open succeeds only if the home image, like every other file, is on a file system whose block is no larger than the unit, and a file's file system does not change while the file is open.
- Where it did apply it protected too little. On such a file system every ordinary write into the home image and the log is exposed, and writing zeros in a hole's place is itself such a write. On the new model of the disk, #21's cut test for the rule (`a_write_zeroes_inside_a_larger_block_can_be_cut_anywhere`) can no longer hold: the zeros written into one unit rewrite the block around it, and its reopen on blocks of four units is refused. I did not run that test against the new model with the rule kept; this is by reading the model.
- A safeguard that cannot be tested honestly is one I would rather not keep. So the rule, `Zeroes::WrittenForBlocks`, its mutant and its two tests are gone. `ZeroesShown::WrittenForBlocks` stays in the status reader with its words, so a status file with the value 3 still reads; the status file is version 4 as before.

### Review round

1. *An open never compared the write unit with the page size of the kernel it runs under* (the lead): a volume made where pages are 4 KiB and opened where they are 16 or 64 KiB passed with a unit below the page, and a kernel writes back whole pages. Fixed, c13f59e: the directory says the system's page size (`Dir::page_size`), and `create` and every open refuse a write unit below it (`StoreError::Pages`, "this system's pages are N bytes, larger than the volume's write unit of M bytes"), in the same place as the block's check and with the same outcome in the daemon (exit 1, the volume not failed). Test `a_store_is_refused_where_pages_are_larger_than_the_write_unit`: a creation under pages of four units makes nothing; a store made under fitting pages is refused under larger ones with no write, sync or change of names, and opens whole again under fitting ones. Mutant `UNDER_ANY_PAGES`, caught in all eight environments. The daemon's own `create` cannot meet this: it chooses a unit of at least the page.
2. *The open asked every name in the directory, opening each read-write* (the lead): a subdirectory, a file without permission or a socket refused a healthy volume with a message about block sizes. Fixed, c13f59e: only the directory and the files the store writes are asked (`home.img`, `home.img.new`, `home.pre`, `log.*`); the lock file and anything else are left alone. Test on real files: `a_stranger_in_the_directory_does_not_refuse_an_open` (a subdirectory and a file of mode 000; the tests here run as root, for whom mode 000 opens, so the subdirectory is the part that failed before).

3. *The exposure test failed at its first stage, the log, so no red run showed the home image's* (the reviewer). Taken, 6a501fb, and it found a real gap in my test. The scenario now also runs with the log's stage left out (every record durable before the first cut). With a write unit of 16 KiB that run lost nothing: in my workload every block near a write was either in the batch or saved as a neighbour. The groups are now 32 blocks wide, with 24 blocks that no record touches, and `a_volume_whose_unit_is_below_the_block_loses_what_nobody_wrote` asserts both: the full scenario loses a flushed record behind a later write, and the scenario without the log's stage loses a block at a checkpoint's cut, each in all four environments that leave garbage. `a_volume_whose_unit_is_at_least_the_block_survives_cuts_anywhere` runs the widened scenario and holds in all eight.
4. *Wording* (the lead). 6a501fb. A refusal for a log segment names the file (`the volume's log file log.000003`); the home image and the preimages are named with their file names. At a start the daemon's line now ends: "Nothing was written and the volume is not failed. A device of this volume that waits for a server is left as it is; `skyzfsd detach` removes it". `create` says on standard error, when the write unit it chose is not the system's page size: `skyzfsd: DIR: the volume's write unit is N bytes, the block size of the directory's file system; this system's pages are P bytes`. I left the `created ...` line on standard output as it is and say nothing in the usual case, because scripts read that line; say if you want the unit printed always.
5. *Padding with a large unit* (the reviewer). The log starts the first record after every sync at the next unit, so with a 64 KiB unit a synced write of 4 KiB takes 64 KiB of log where it took 8 KiB with a 4 KiB unit: the high mark comes up to eight times sooner under small synced writes, and with it the checkpoint steps. Not measured.
6. *Network and cluster file systems* (the reviewer): they report their transfer size as `f_bsize` and are refused above 64 KiB; there is no override. No code; the lead writes what is supported into the design.

## How it was verified

At 6a501fb (the review round): the same gates, all clean; `cargo test --workspace`: 1135 passed, 0 failed, 16 ignored; with the test hooks: 253 passed, 0 failed, 3 ignored; `skyzfs-ublk-sys --features control-test-program`: 7 passed, 11 ignored. The counts below are those of 06b77f9, and the description of the cut scenario below is the first version's (groups of 8 blocks, 32 of them); it now has 16 groups of 32 blocks.

Locally at 06b77f9 (stable 1.99.1; no ublk in the container): `cargo fmt --check` clean; `cargo clippy -D warnings` clean for the workspace and for `skyzfsd --features test-hooks`, `skyzfs-ublk-sys --features control-test-program`, `skyzfs-local --features test-hooks`; docs of the four crates with `-D warnings` clean; `cargo test --workspace`: 1133 passed, 0 failed, 16 ignored; `skyzfsd` and `skyzfs-local` with their test hooks: 251 passed, 0 failed, 3 ignored; `skyzfs-ublk-sys --features control-test-program`: 7 passed, 0 failed, 11 ignored (the kernel tests).

Tests, in `crates/skyzfs-local/src/store/tests.rs` unless said; "all eight environments" are record alignment 64 and 4096, write unit 4096 and 16384, a power cut that leaves what was lost as it was or as garbage.

- `a_store_is_created_only_where_blocks_are_no_larger_than_the_write_unit`: blocks of 512, 4096 and one unit: created. Blocks of two and four units and of 1 MiB: `Blocks`, with the sizes, and the disk has no file and no write. A size that cannot be read: `BlocksUnknown`, no file. Mutant `CREATE_ON_ANY_BLOCKS` (the check at create is not made): caught in all eight.
- `an_open_is_refused_where_blocks_are_larger_than_the_write_unit`: a store with a flushed write and an unflushed one is killed; its disk then reports larger blocks, or none: the open is refused, the disk's counts of writes, syncs and directory syncs and its list of names are as before; with fitting blocks again the same store opens and holds both writes. Mutant `OPEN_ON_ANY_BLOCKS`: caught in all eight.
- `a_volume_whose_unit_is_at_least_the_block_survives_cuts_anywhere`: the disk's own write unit is one sector, so the file system's block alone says how far a write reaches; block = the volume's unit, and block = 512. Per stop point (34 of them): a write is flushed, two more are not, power cut, the flushed write is there (the log); then 32 groups of a zeroed range and a single-block write beside blocks only the home image holds, the checkpoint's steps stopped at that point, power cut, the open stopped and cut again; content checked after the open and after the remaining steps. Holds in all eight.
- `a_volume_whose_unit_is_below_the_block_loses_what_nobody_wrote`: the same scenario with both checks off (the store as it was) on blocks of four units: it loses something in each of the four environments that leave garbage. This is the exposure, kept as a test.
- Simulated disk (`sim.rs`): `a_write_rewrites_its_whole_file_system_block`; the directory says the same size as its files, and an error where none is set.
- `format.rs`: `the_write_unit_is_at_least_the_file_systems_block` (512 to 4096 give the page; 16384 and 65536 give themselves; 0, 3000, 12288, 131072, 1 MiB and 2^40 give none).
- `skyzfsd`: `create_chooses_the_write_unit_by_the_file_systems_block_or_refuses` (the three refusals' words); `skyzfs-ublk`: a `Blocks` error is sorted as a refusal with its reason, not as a failure.
- Real files: `a_real_file_says_its_file_systems_block_size` now also asks the directory. Every existing test on real files creates and opens through the new checks on the container's file system (4 KiB blocks).

On a kernel this package should change nothing: the runners' ext4 has 4 KiB blocks, `create` chooses the page size as before and every open passes. The pull request's rigs show that.

## Not done, and open questions

- **Not verified on a real file system with blocks above the page size.** Neither that XFS there rewrites whole blocks around a buffered write (the premise, from the review of #21, not from the kernel's source), nor that `f_bsize` reports that block size, nor a real refusal. Whether a runner can make such an XFS is with testing.
- **Not verified: what `f_bsize` is on each file system.** From memory, not from a source: ext4, XFS and btrfs report their block (sector) size, tmpfs the page size, a network file system its transfer size. A file system that reports less than it rewrites would pass the check wrongly; I know of none.
- **The simulated disk has one file system**, so "a file on another file system than its directory" is covered by code (the open asks every file) and not by a test.
- **A volume created before this package on a file system with larger blocks** is refused at its next open. No such volume is known; if one exists, its data is as safe as it was, and it is read by copying the directory to a file system with fitting blocks.
- **macOS and Windows**: no block-size call, so no store there until one is built (see above).
- The kernel step with preludes is still my temporary copy on the run-only branch `skyzfs-coding-m1.3b`, until M1.T8.

**For §5.1 at the merge**, a proposal: "A volume's write unit is the larger of the page size and the block size of the file system its directory is on, at most 64 KiB. An open under a kernel with larger pages than the unit is refused in the same way as one on larger blocks. `create` refuses a file system with larger blocks, blocks that are no power of two, or a block size it cannot read. Every open checks the directory and each file again, before it writes, and refuses a volume that now sits on larger blocks (exit 1, with the reason; the volume is not failed). The limit 'a volume's directory must be on a file system whose block is no larger than the page' is replaced by this. The rule that a range is deallocated only where the block is no larger than the write unit is gone, and the status value 3 of `zeroes_applied` is no longer written."

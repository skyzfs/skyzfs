## Work package

M1.3m: the home image's sync leaves the worker.

After M1.3k, the first slow-sync benchmark job with the writeback hint (run 43218763894, one run per row) still showed the home image's sync as the largest cause of a write's wait: 939 of 2049 µs, at 29.3 ms per step with 95% of its bytes already handed to the device. On a disk that writes about 200 MiB/s, a step's 8 MiB take about 40 ms whatever starts their writeback. The worker waited through all of that time and served nothing.

This package hands that sync to a helper thread. The worker applies a step as before, starts the sync on the helper, and goes on serving appends, flushes and its own syncs of the log. When the helper reports, the worker takes the step up again: the log's new start, the index's drop, the second barrier. This is shape (b) of the coding session's one-page comparison, which the lead chose over (a), the whole step on a thread of its own.

Commits: `e8746ae..19ca666` on `skyzfs-coding`. Files:
- `crates/skyzfs-local/src/io.rs`: a sync that ends later (`File::sync_begin`, `sync_end`, `sync_wakes`, `HelperEnded`); by default the whole sync is made at the end, as before.
- `crates/skyzfs-local/src/fs.rs`: on real files, one helper thread per file with its own descriptor, started at the first use and joined when the file is dropped.
- `crates/skyzfs-local/src/sim.rs`: the simulated disk's sync that ends later, and the hooks the tests use: a seeded delay, holding a file's syncs, counting the callers that wait for a held sync, counting writes per file and writes made while a sync is under way.
- `crates/skyzfs-local/src/store.rs`: the step split at the home sync (`apply_writes`, `finish`), the hand-over (`apply_handing_over`), the report (`report`, `settle`), the rule and the worker, two mutants, and timing.
- `crates/skyzfs-local/src/lib.rs`: the crate's documentation gains "The home image's sync on a helper".
- `crates/skyzfs-ublk/src/status.rs`: status version 8.

- Tests: `store/tests.rs`, `store/harness.rs`, `tests/store_real.rs`, `status/tests.rs`, `cli/tests.rs`, and the tests in `sim.rs` and `fs.rs`.

| 1. One long-lived helper. The worker applies as today, hands over "fdatasync the home image", serves appends, flushes and own syncs, and takes the step up on the report. Meanwhile no next step and no write or deallocation in the home image | A step of the checkpoint rule writes its batch exactly as before (saved neighbours, first barrier, writes, the pause point `Written`) and then calls `sync_begin` on the home image. On real files that sends the sync to the file's helper thread, which runs `fdatasync` on a descriptor of its own and then wakes the worker. The worker asks for the report at the top of every turn, without waiting. When the report has come, it runs the rest of the step as before (`Synced`, the reclaim, `StartWritten`/`StartDurable`, the index's drop, the second barrier). While a step's sync is out, the rule takes no step (`tend` returns early), so nothing writes to the home image. A test shows this on the simulated disk, which counts writes made to a file while its sync is under way. A served store always hands the sync over. A store that is not served does so only with `OpenOptions::hand_over_home_sync`, which the tests use |
| 2. The worker then goes on taking steps before the next request, as before. That wait is the time the worker would have spent in the sync itself. The test `at_the_high_mark_the_worker_waits_for_the_report` shows it, and checks that the log stays below the high mark plus one request |
| 3. make_room, the explicit checkpoint, the hold, stop and detach wait for the report first | `Core::checkpoint` (used by an explicit checkpoint and by `make_room`), `Core::checkpoint_step`, `Core::set_hold` and the worker's end all call `settle`, which waits for the report and takes the step up. `Served`'s drop now sends the worker a `Stop` command, because the worker itself holds a sender for the helper's wake. `skyzfsd detach` reaches the store as the serving daemon's orderly end, which is that same drop, so at the store's level stop and detach are one path; no test of mine covers detach through the daemon (that needs a kernel) |
| 4. A failed sync is handled as today's failed home sync. A helper that ends or panics is the target's end | A failed sync fails the volume and marks the log, as the worker's own failed sync would. If the volume failed for another reason while the sync was out, the step is not taken up when the report comes (conservative reading). A helper that ends without a report (it panicked) is the end of the served store: the worker returns, as when it panics itself. The log is not marked, because its start has not moved and the next open applies the batch again (conservative reading). On the real file the wake is called by being dropped, so a helper that panics still wakes the worker, which then finds it gone. `fs::tests::a_sync_is_done_by_the_files_helper` shows this |
| 5. The kernel call is passed to the store only when either unit is nonzero, so `--writeback-kib 0` with the default home unit is still the daemon as it was before M1.3k. I saw no reason against turning it off |
| 6. The simulated disk: "sync begun" and "sync done" as two points of the worker's one schedule, the completion point chosen by the seed, no real thread | `sync_begin` notes how many unsynced versions each sector has. The end makes exactly those durable, together with the file's length at the begin; later writes stay unsynced. That is `fdatasync`'s promise, which covers what was written before it was called. The end comes at the first `sync_end`, or with `set_sync_delay(n)` after up to n calls that do not wait, as many as the disk's seed chooses for each sync, or when a caller waits. It counts as a write or sync for `halt_after` at its end, not at its begin. With no delay the seed is not drawn from, so every existing seeded test sees the same disk as before. A served store on the simulated disk looks for the report every millisecond while it waits for work, because nothing wakes it |
| 7. It is at offset 1856, and each kind of request's wait by it follows at 1864. Every field of version 7 stays where it was. Then come the helper's syncs (count, sum, longest, from the hand-over to the worker taking the report), the worker's waits for the report (count, sum, longest), and the requests completed while a sync was out. The sixteen activities follow each other with no gap, as the fifteen did, and the existing exactness test passes. `step_home_sync` is now the worker's part in the sync: the whole sync where the worker makes it, and the hand-over where the helper does, so there is still one per batch. A step's sync under `syncs[home]` counts from the hand-over to the report. `skz_time.py` knows version 8's keys (`KEYS_ADDED[8]`), puts `step_report` in the step's group, and prints a table of the helper |
| 8. What each point says about the disk is unchanged: at `Synced` the home image is durable and the log starts where it did |

**The waits were checked by hand as well.** I removed each wait in turn and ran its test:
- the settle in `Core::checkpoint`: the checkpoint test and the room test both fail ("no wait for the report");
- the settle in `set_hold`: the hold test fails;
- the settle at the worker's `Stop`: the end test fails;
- the wait at the high mark in `tend`: the high-mark test fails.

**Why the existing cut tests keep their argument.** They drive a store that is not served and does not hand the sync over (the option is off), so their order of disk operations is the one they had. Where a served store on the simulated disk hands the sync over with no delay, the sync ends at the first look, inside the same call. The order of writes and syncs is then the one it was: the begin is not counted for `halt_after`, the end is, at the same place as the old sync. The seed is not drawn from without a delay. So every existing test sees the same disk. The new cases between the two points are covered by the cut test above and by the conformance suite with a delay.

## Not done, and open questions

- **No kernel run of mine.** The control rig and the daemon rig run on this pull request (`crates/skyzfs-local/` is touched). The daemon rig's kills at a step's points keep their meaning. What is new on a kernel is a kill while the helper syncs, with appends after the hand-over, which the rig's kills under load can hit.
- **Conservative readings, also marked in the code:**
  - a volume that failed while a sync was out does not take the step up when the report comes;
  - a helper that ends without a report ends the served store and leaves the log unmarked;
  - a change of the hold goes ahead after a wait for the report even when that report failed the volume;
  - `stepping` (status "checkpoint_step under way") stays set until the report has been taken;
  - `step_home_sync` holds the hand-over where the helper syncs, so the step still has six parts with one each per batch;
  - a served store on the simulated disk looks for the report every millisecond while it waits for work.
- **Things to measure, not designed around:**
  - whether the helper's `fdatasync` and the log's couple through the file system's journal (on ext4 a punched hole makes the home image's sync commit the journal);
  - the superblock's sync on slow-sync machines;
  - a client's flush can now wait for a device that is busy with the home image's 8 MiB.
- **The write call from 102 to 251 µs with the log's hint (37 µs of it the hint): not explained.** The handed range does not end inside a page here (above). A candidate I have not checked: a new segment file's 64 MiB of zeros is handed over at once when the file is made. The appends that follow write into those same pages, which may still be under writeback. On a device that requires stable pages (`/sys/block/<dev>/queue/stable_writes` is 1), each such write waits for that page's writeback. The testing session could read that file on a slow-sync runner. If it is 1, leaving the zeros to the next sync, instead of handing them over, is a few lines. On a system with 64 KiB pages (some arm64 kernels), records of 4096 would share pages, and the range would end inside a page; handing over whole pages only would be the fix there.
- **Not in this package:** the log's own sync and a client's flush on a helper (the lead's choice (i)).

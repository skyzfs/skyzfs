## Work package

M1.3d: a failed volume holds no request. When a volume's store fails, the daemon deletes the volume's device. The driver's delete of a device that is being served waits, with the driver's control lock held, for every request the server still holds (seen by the testing session in run 43074927907). Before this package the daemon could hold requests for as long as the failed disk took: requests in the store, and completions that waited for the acknowledged position, which is recorded on the same disk. The delete, and with it every other add or delete of a ublk device on the machine, could wait as long.

Commits: `957e74b..00a5ecc` on `zfs-topology` (9 commits of its own, three more after the first review (a811645, d02e8f6, 00a5ecc; their own section below), and one merge of `zfs-topology` at c9c87df, where M1.3c, skyzfs/skyzfs#17, is merged; the difference to the base is this package alone). Design: docs/skyzfs-design.md §4.1 (the pump), §4.2 (what was acknowledged, a failed volume).

### A rule change, decided by the lead: read it as a decision, not as a test edit

Before: a start that refuses, for want of `--acknowledge-failure`, a failure nobody held touched nothing at all (the design's point 4, and two tests said so). If the daemon that failed had been killed between writing the failure note and its delete, the volume's device was left waiting for a server; every such start left it there, and it held whatever was sent to it, without limit and without a word.

Now: **whoever holds the volume's lock and finds the failed volume's device waiting deletes it.** The start that refuses a held failure, the start with the flag and `detach` did this already; the refusing start now does too, through `give_up_device` with its conditions unchanged (the device carries this volume's note with the recorded values, and is not live). It says what became of the device: deleted, left and why, or that none was there. It still touches nothing the decision rests on: the failure note, the acknowledged position and the marker stay, the exit status is 4, the next start without the flag refuses again, and one with it serves afresh as before.

The two tests state the new rule: `an_unheld_failure_not_acknowledged` (the events are exactly features, the lookup, the note's removal, the delete; note, position and marker as before; a second refusing start finds no device, says "no device of this volume was there" and deletes nothing) and `an_acknowledgement_killed_anywhere` (a start that asks touches nothing but the waiting device, and says what became of it, at every kill point). Mutants: the delete is not said; the refusal changes the note. The delete itself does not wait for a holder (it is the driver's delete without waiting, of a device that is not live); it can wait behind another device's delete that the driver is carrying out, and nothing bounds that here, as nothing does in `fail_serving`.

### What the merge with M1.3c had to reconcile

One conflict, two lines in `bins/skyzfsd/src/serve.rs`: both packages changed the call the queue's thread makes after every turn. This package put `answer_if_failed` before the post of the counters; M1.3c gave that post the log's state. Both are kept, in that order. `status.rs` merged by itself (M1.3c's log fields and this package's `failure_device` and `failure_pool` lines are in different places). Nothing else met. One thing follows from the two together and is as it should be: a failed pump still posts its counters and the log's state after every turn, so the status file goes on being written while the daemon answers errors.

### The points the package was asked to settle

- **A completion that waited for its position at the failure is answered with the I/O error, not left for a reissue.** A reissue needs a next instance, and a failed volume has none in this boot: the device is deleted. Committing its own result is out: it may say "written" for a position nobody stored. An I/O error promises nothing, so it is always a permitted answer; the write may be in the log and may be applied by a later open, and a client that was told "failed" cannot rest on either.
- **Late completions and the buffers.** After the failure the pump never takes a completion from the store, so there is no late completion to drop and no tag to confuse: a tag answered at the failure can be another request's a moment later. The buffers of the reads and writes the store held stay in the store, which lives until the process ends. The queue makes a new buffer for a tag that is committed without one (the binding did this already), so the driver is told a new address, and the old ones are not given back to the allocator while the queue lives.
- **A store call that hangs and never fails** sets no failure, and nothing in this package bounds it. Today: the request stays held; a stop waits for the store to drain and so never ends; the operator's way out is `kill -9`, after which the device waits for a server and the next instance is issued the requests again, which is safe and not orderly. A bound would go in one of two places. (1) In the pump's stop: after a stated time leave what the store holds to the next instance, as it does for unstored completions now (the module text has had this as "for M3, not built"). Cost: none in data; but the process then has to end with a worker inside a system call, see the next point. (2) In the store: a watchdog that declares the volume failed when a call has not returned in a stated time. Cost: a figure that is wrong for some disk, and a volume failed for a disk that was only slow; it turns a wait into errors on the pool. Neither is built.
- **Can the process end while the store's worker is stuck?** Not today, and on purpose it is left so: dropping the store joins its worker, and the main thread holds the volume's lock until then. A worker inside a write may still write; while it can, no other instance should get the lock. So after a failure the device is deleted and its requests are answered promptly, and the process may then linger for as long as the disk holds the worker (the failure marker alone "may take minutes" by the store's own text). Whether a thread in an uninterruptible wait lets the process be killed at all is the kernel's matter and was not measured.
- **What "deletes regardless after 2 s" means for the node.** Two cases, and only the second is a wait.
  - *The store still holds a request at the delete.* This is the ordinary failure, and it no longer matters to the driver: the pump has answered that request with the I/O error, so the server holds nothing in the driver's eyes, and the delete does not wait. The store may go on with the request for as long as the disk takes; what it completes is never taken.
  - *The queue's thread is itself stuck*, inside a call that does not return: the one such call it makes is storing the acknowledged position (in the run directory, which I wrongly called the failed disk at first; since the review that record refuses once the failure is known, so only a write that began before can hang). It then answers nothing, the 2 s pass, and the delete is sent all the same. That delete waits in the driver, with the driver's control lock held, until the stuck call returns and the thread answers or ends. For that long every add, delete and lookup of any ublk device on the node waits behind it, the other volumes' daemons included (their serving goes on; their starts, stops' deletes and detaches wait), and this daemon's main thread is inside the delete and cannot end. The daemon says so on standard error before it sends the delete ("did not answer what it held within 2000 ms: device N is deleted all the same, and the delete waits in the driver for as long as a request is held"), since that line may be all an operator gets for a long time. Not deleting would leave a live device whose requests hang instead. This is the case the design's open decision is about, and it is not bounded here: a bound needs either the position stored off the queue's thread, or a deadline on that call.

## What is not solved

**A pool imported on the device does not notice that the device is gone while it only writes, and the daemon does not make it.**

*Established* by the testing session on the daemon (runs 43093721420, 43100887191, 43100211375, one per image each) and from the source (`zio_done` in OpenZFS 2.4.1; design §4.2, footnotes `[^refwr]` and `[^zioreexec]`): after a refusal with the device deleted, the pool's writes fail at once and ZFS executes each failed allocating write again without end. That is its design for every error but "no space"; only a failed read or free suspends a pool. So the pool reads ONLINE with one transaction group syncing for ever and write errors in the tens of millions. With a log device a synchronous write was still acknowledged minutes later (5 of 6); without one it hung (2 of 2). The first read that had to reach the device suspended the pool within a second or two: a read of an uncached file (4 of 4), the start of a scrub (2 of 2).

*What the daemon does about it:* it says it. The decision is the lead's: the daemon is below ZFS, the device is gone and it knows no pool, so it does not act on one. Every line of a failure or a refusal ends with the warning, and `skyzfsd status`, with no daemon running, reports the failure, what became of the device (`failure_device`) and the same warning (`failure_pool`): "a pool imported on this volume's device does not notice that the device is gone while it only writes: it goes on reading ONLINE and, with a log device, acknowledging synchronous writes that never reach the volume. A read that must reach the device suspends it (for example `zpool scrub POOL`), and the pool cannot be imported again before a reboot". Before this package `status` in that state gave the state line and the failure's reason, holding, boot and age; nothing on the device unless it still carried the volume's note, and nothing on the pool.

*Whose step the read is:* the operator's until the agent exists (M2), then the agent's.

*Not measured yet:* which command is the surest read; what an export, a reopen and a clear do in that state; what zed does; and whether the course is the same after a failure while serving, where this package's failure path answers held requests with an error before the delete (the testing session measures that once this is merged).

*Not a way out:* having the daemon serve the device a while longer and answer everything with an error would not help: ZFS re-executes failed writes whatever the error, and an idle pool sends no read to be failed.

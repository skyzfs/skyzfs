## Work package

M1.3k: writeback started early.

Benchmark round 2 (60e4c7c, three runs on slow-sync machines, one run per figure) showed reads fixed by M1.3j and writes still waiting 2.31 to 2.59 ms, 91 to 93% of it behind the checkpoint step's sync of the home image and the rule's own sync of the log. Those syncs are linear in the bytes written to the file since its last sync: about 200 MiB/s on slow-sync machines, about 2 GiB/s on fast ones. The store writes through the page cache, and nothing starts the writeback before `fdatasync` does, so a sync waits for the device to write the file's whole backlog. This package asks the kernel to start that writeback early, once a unit of a file's writes waits, so that the sync that follows has less left to wait for. It is a hint: every sync stays where it is, and nothing about order, durability, the marks or the checked read changes.

Commits: `26c6f91..4ccbfe9` on `skyzfs-coding` (built on M1.3j, #29). Files:
- `crates/skyzfs-local/src/io.rs` (the trait's hint), `writeback.rs` (new: when to give it, what it counts), `log.rs`, `store.rs`, `fs.rs` (the hook), `sim.rs` (the simulated disk's hint);
- `crates/skyzfs-ublk-sys/src/writeback.rs` (new: the one `unsafe` call), `crates/skyzfs-ublk/src/volume.rs`, `crates/skyzfs-ublk/src/status.rs` (version 7, `status_version`);

## What `sync_file_range` does here

From the man page `sync_file_range(2)` and the source of `fs/sync.c` (`ksys_sync_file_range`) and `mm/filemap.c`, as far as I can tell; nothing here was checked on a kernel:

- **What it does.** With `SYNC_FILE_RANGE_WRITE` alone, it calls `__filemap_fdatawrite_range` with `WB_SYNC_NONE`, which runs the file system's `writepages` over the dirty pages of the range and submits them. It does not wait for them, writes no metadata, and promises no durability. `WB_SYNC_NONE` skips pages already under writeback instead of waiting for them.
- **Errors.** It does not wait, so it does not call `file_check_and_advance_wb_err`. That happens only with `SYNC_FILE_RANGE_WAIT_BEFORE` or `WAIT_AFTER`, in `file_fdatawait_range`. An I/O error of the writeback it started is recorded on the mapping as any writeback error is (`mapping_set_error`), and the next `fdatasync` of the file reports it. So the hint cannot hide an error from the sync that follows. An error returned by the call itself (from submitting) fails the volume here in any case.
- **Can it block?** Yes, for submitting, not for the device to finish. The man page says that "even this may block if you attempt to write more than request queue size": bio submission waits for a free request (tag) of the device's queue. It can also wait on a page's lock while it takes the page, and on whatever the file system's `writepages` waits for.
- **ext4 with delayed allocation.** A delayed-allocation page gets its blocks in `writepages` (`ext4_writepages`, `mpage_map_and_submit_extent`), which starts a journal handle and can wait for the journal. The store's files are written over blocks that are already allocated: segment files are preallocated with written zeros, and the home image is written whole at create. So their writeback needs no allocation and no unwritten-extent conversion, and the hint should only submit I/O. A new segment file's zeros are the exception: written by `preallocate` and handed over at once.
- **XFS.** The same shape (`xfs_vm_writepages`, iomap): overwrites of allocated, written blocks need no allocation transaction.
- **What it means for the worker.** The worker makes the call between requests (the log's hint within a write's call, the home image's within the apply). On a queue that is full it waits for a free request. With the unit at 1 MiB that is at most one unit per call, and it is time the following `fdatasync` would have spent anyway. The hint's time is counted (`time_writeback_*_ns`), so a reading shows whether it blocks.

## Not done, and open questions

- **No kernel run of mine.** Whether the hint shortens the syncs on a runner is for the benchmark to say: `--writeback-kib 0` and the default on one machine, with the new tables. My expectation:
  - for the log, writes spread over seconds between syncs, so most of an own sync's backlog should be handed over before it begins;
  - for the home image, the apply writes 8 MiB in a few ms just before the sync, so the gain there is at most the apply's own length of device time.
- **The rig's coverage.** The daemon rig and the control rig run on this pull request (`crates/skyzfs-local/` and `crates/skyzfs-ublk-sys/` are touched).
- **The hint's behaviour on ext4 and XFS** is as the documentation and source say (above), not measured. The new `time_writeback_*_ns` shows what it costs.
- **The preimage file has no hint** (above).

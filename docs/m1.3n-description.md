## Work package

M1.3n: several readers, and what the status thread costs.

With the daemon bounded to 1 GiB of memory, the benchmark showed tps at 0.856 of the model on the slow-sync machine and 0.925 on the fast one, against 0.920 and 0.959 unbounded. The reads then go to the disk: the store's read call took 254 µs (56 µs unbounded), and a read waited 222 µs for the reader (64 µs unbounded), with the one reader thread busy 0.52 of the window. Reads were queueing behind each other on one thread. Part 1 gives a served store several reader threads (design §5.1 "Reads leave the worker").

Part 2: the status thread took 2.8 s of CPU in a 120 s window, which is a lot for a file of 1960 bytes written a few times a second.

Commits: `07be854..7894d66` on `skyzfs-coding`: 4362b6c (part 2), 28c25f6 and 10132be (part 1), and 7894d66, which merges `zfs-topology` after #33 had merged. The work began at 34dcf39, the head of #33, and against `zfs-topology` the branch shows only this package. Files:
- `crates/skyzfs-local/src/store.rs`: `OpenOptions::readers`; N reader threads in `Store::serve_with`; the readers' times summed in `Shown::both`; the test hook `Store::set_read_pause_at`; the mutant `BARRIER_WAITS_FOR_ONE`.
- `bins/skyzfsd/src/cli.rs`, `serve.rs`: `serve --readers N`.
- `crates/skyzfs-ublk/src/status.rs`: when a post wakes the status thread.

## What was done

| Asked | Done |
|---|---|
| `serve --readers N`, default 4, 1 is today's daemon; a store that is not served is unchanged | `OpenOptions::readers` (1 in the library, where 0 counts as 1). `skyzfsd serve --readers N` takes 1 to 64 and is 4 unless given. A store that is not served has no readers and nothing changes for it. With N readers the store opens the home image N times, one handle per reader. The readers take reads from one queue, a `Mutex<Receiver>` that an idle reader holds while it waits. A read goes to whichever reader is idle, and reads complete in any order. Nothing about what a read promises changes: a read submitted after a write was acknowledged looks up after it, whichever reader takes it |
| Every property of M1.3j holds for each reader | Each reader runs the same `Reader::read` as before, on handles of its own. It takes its pin before its lookup, holds the lookup's lock for the lookup alone, makes the checked read of a record that is not yet durable, and hands a mismatch to the worker (`Command::ReadFailed`, as before). The failed flag is the shared one, set only after the log's mark. The barrier was already counted by generation and waited for every reader of an older one, so it needed no change. The worker is unchanged |
| (a) A read held inside its file read while another read of another block completes, resting on events | `a_read_held_in_one_reader_leaves_the_others_reading`, in every environment. Two readers. A read of block 0 is held after its lookup, with its pin, by a gate on that block only (the new hook `set_read_pause_at`; the hook of M1.3j held every read). Two reads submitted after it, one from a record of the log and one from the home image, complete and return their blocks while it is held. Released, it returns its block. With one reader (changed by hand), the test fails: "the reads beside the held one: 0 of 2 completions" |
| (b) Each barrier waits for a pin held by any of the readers, with two readers pinned and released one after the other | `each_barrier_waits_for_every_reader_that_is_pinned`, in every environment and in both orders of release. First barrier: two reads of blocks only the home image holds are held; writes to both blocks are made durable, and a checkpoint is asked for. Second barrier: two blocks in records of the first segment file are held while the step stands where it frees that file, and a megabyte that needs the freed file is written behind it. When the first reader has completed, the test waits until the barrier has woken and looked again. That is an event, counted under the barrier's lock in the same hold as its passing. The barrier must not have passed, the step must not have written, and the write behind it must not have completed. Then the second reader is released, and both reads return their blocks as they were. **New mutant `BARRIER_WAITS_FOR_ONE`** (the barrier waits until one of the readers it found has left) is caught at both barriers in every environment, and so are `HOME_WRITTEN_UNBARRED` and `SLOT_REUSED_UNBARRED` with two readers |
| (c) PIN_AFTER_LOOKUP still caught with N > 1 | `several_readers_hold_their_pins_from_before_their_lookups`: with two readers, the mutant is caught at both barriers in every environment, by the held reads returning what the step wrote |
| (d) The conformance suite while it checkpoints in steps, served with N readers, in every environment | `the_store_passes_the_conformance_suite_while_it_checkpoints_in_steps`: the served variant with a sync delay now has three readers, and the served variant without one keeps one. I changed a variant instead of adding one so the suite's time stays as it was (115.7 s for the whole test locally) |
| (e) The time account, with an exact identity | No new status version. `Timing::reader` is the sum over the readers of each reader's idle, call and other, in thread-nanoseconds. `reader_as_of_ns` is the sum of each reader's moment, as M1.3k defined it for one thread. So between two looks the readers' activities sum to the difference of `reader_as_of_ns` exactly, with any number of readers. That difference is about N times the time between the looks, and a share of the sum is the readers' share on average. A read's wait (`requests[0].wait`, `wait_by[0]`) is laid over the reader that took it, so its causes still sum to its wait. `longest_wait_cause` is the one of the reader with the longest wait. The test `the_threads_times_sum_to_the_time_between_two_looks_exactly` now runs with one reader and with three. With every thread idle, it also waits for two looks between which the readers' moment moved by exactly three times the worker's. `skz_time.py` needs no change for its identity or its shares, but its row does not show N: see below |
| Not wanted: reads on the pump's thread or in its ring; any change to the worker | Neither: the pump and the worker are untouched |
| Part 2: how often the status thread writes, and what the time is; at least five times less, no reading staler than 200 ms, `ready`'s promise unchanged | **What it was:** the queue's thread posts the counters and the log's state after every turn, and every post did a `notify_all` that woke the status thread, also while it was only waiting out the 100 ms interval. Each wake took the lock, compared, and waited again. The writes themselves are few: at most one per 100 ms, plus one at the begin and the end of each step. Each is a create, a write of 1960 bytes, and a rename, with no sync. Measured with a post every 20 µs for 3 s (the board and the writer of the daemon, on this container's file system, release build): the thread took **95 ms of CPU a second**, of which 9 ms were its 53 writes (0.5 ms each here). **Now:** a post wakes the thread only when it waits for a change, or when it asks for a write at once (a step's begin or end). While the thread waits for the end of an interval, the write at that end takes whatever is posted by then. Measured the same way: **5.9 ms of CPU a second**, 16 times less. The posting side got cheaper too: in the same 3 s, 145,435 posts against 102,741, because a post no longer pays for a wake. **Staleness and `ready`:** a reading is no staler than before, at most one interval (100 ms) behind the last post. The interval is unchanged, so check c's condition holds: while the counters change, the file is written at least every 250 ms. The first write, which `ready` waits for, is due at once as before. Test: `a_post_wakes_the_publisher_only_when_it_waits_for_a_change`. Over 20,000 posts it requires at most 3 wakes per write plus 3, and that the last counters posted are written. **Mutant `WOKEN_BY_EVERY_POST`** is caught |

## Not done, and open questions

- **No kernel run of mine.** I have not measured what four readers do to the bounded benchmark. That is the testing session's run: one runner, `TB_SKYZFSD_MEM` at 1 GiB, `--readers 1` against 4.
- **The benchmark's row does not say how many readers it ran with.** The status file does not hold N, and I added no version for it. The readers' identity holds with any N, and their shares are averages. The topology `zfs-skyzfsd` passes no `--readers`, so it now runs with 4. If a row must state N, the benchmark script (the testing session's) can put the flag in its label, or a status version 9 can carry it. I did neither without a decision.
- **Conservative readings, also marked in the code:**
  - 0 readers counts as one in the library, and the daemon refuses 0;
  - the time a reader waits for the queue's lock (another reader holds it while it waits for a read) counts as idle;
  - `Served::panic_reader` (tests only) now waits for the store's end and not for a thread's join, as it cannot know which reader took the panic.
- **What the readers share:** the lookup's lock (a `RwLock`, read-held for a lookup) and the queue of reads. With N readers, each opens the home image once and opens each segment file when it first needs it: up to N × (1 + segments) descriptors.
- **Part 2's other costs, not changed:** each write still reads `/proc/uptime` and builds the file with create, write and rename. At ten writes a second that is a few milliseconds a second here.
